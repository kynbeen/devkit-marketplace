description: 지금까지의 작업 상태를 docs/handoffs/ 에 기록하고 커밋·푸시한다 (기기 전환 또는 /clear 직전에 사용)
---

이 세션의 작업 상태를 인계 문서로 남긴다. 사용자가 곧 `/clear` 를 하거나 다른 기기로 옮길 예정이므로,
**이 문서만 읽고도 작업을 이어갈 수 있어야 한다.**

사용자가 준 설명: $ARGUMENTS

## 1. 사실 수집 (먼저 실행)

```
git rev-parse --is-inside-work-tree     # git 리포인가
git status --short
git diff --stat HEAD
git log --oneline -5
git remote                              # 원격이 있는가 (비어 있으면 푸시 불가)
```

기기 이름 — **추측하지 말고 반드시 실제 값을 쓴다.**
- Windows(PowerShell): `$env:COMPUTERNAME`
- macOS/Linux: `hostname`

**git 리포가 아니면** 2·4단계(커밋·푸시)를 건너뛰고 문서만 저장한다.
이때 반드시 사용자에게 알린다: *"git 리포가 아니라 문서만 저장했다. 다른 기기에서는 이 문서를 볼 수 없다."*
조용히 넘어가지 말 것 — 인계가 안 됐는데 됐다고 믿는 게 최악이다.

## 2. 코드부터 따로 커밋한다 (중요)

작업 트리에 커밋 안 된 변경이 있으면 **인계 문서를 쓰기 전에 그 코드부터 별도 커밋**한다.
사용자에게 무엇을 커밋하는지 알리되, 이 순서 자체는 묻지 말고 지킨다.

이렇게 하는 이유: 코드와 인계 문서를 한 커밋에 섞으면 "이 문서가 설명하는 코드 상태"가
그 커밋 자신이 되어버려 앞뒤 관계가 모호해진다. 코드 커밋 → 문서 커밋 순서로 분리하면
**인계 커밋이 '여기까지 정리됨'을 나타내는 깨끗한 표식**이 된다.

(커밋할 변경이 없으면 이 단계는 건너뛴다.)

## 3. 문서 작성

경로: `docs/handoffs/YYYY-MM-DD-NN-<설명>.md` (`docs/handoffs/` 가 없으면 만든다)

- 날짜는 실제 오늘 날짜(시스템 날짜나 위 `git log` 의 최신 커밋 날짜로 확인 — 추측하지 말 것).
- **`NN` 은 그날의 순번**(`01`, `02`, …). `docs/handoffs/` 를 훑어 같은 날짜 파일을 세고 다음 번호를
  붙인다. 두 자리 고정 — 하루에 10개가 넘어도 파일명 정렬이 시간 순서와 일치해야 한다.
  **이 순번이 "가장 최근 핸드오프"를 찾는 유일한 근거이므로 빠뜨리지 말 것.**
- `<설명>` 은 `$ARGUMENTS` 를 짧은 슬러그로 변환(공백→하이픈, 경로 문자 제외).
  `$ARGUMENTS` 가 비어 있으면 이번 세션 내용에서 직접 요약해 짓는다.
- **기존 파일을 덮어쓰지 않는다.** 번호가 겹치면 다음 번호를 쓴다.

아래 섹션을 모두 채운다. 빈 섹션은 "없음"이라고 명시한다(섹션 자체를 지우지 말 것):

```markdown
# <제목>

**날짜:** YYYY-MM-DD
**기기:** <실제 호스트명 그대로. "데스크탑"/"노트북" 같은 별칭으로 바꾸지 말 것>
**관련 명세:** <`docs/specs/…md` 경로. 없으면 "없음">

## 현재 상태
지금 무엇이 어디까지 됐는지. 한 문단.

## 이번 세션에 한 일

## 내린 결정과 근거
"왜 그렇게 했는지" — 나중에 되돌리고 싶어질 결정일수록 이유를 반드시 남긴다.

## 고려했다가 안 한 것
| 대안 | 왜 안 했나 |
이번 세션에 검토했지만 접은 경로. 사용자가 거절한 제안도 여기 적는다.
(이 중 **계속 유효한 것은 아래 4단계에서 명세로 옮긴다** — 여기 있는 건 이번 세션 기록일 뿐이다.)

## 변경한 파일
| 파일 | 무엇을 / 왜 |

## 미해결 질문 / 블로커

## 다음 단계
바로 착수 가능한 형태로. "X를 검토한다"가 아니라 "X 파일의 Y 함수를 Z로 바꾼다".

## 재개 시 읽어야 할 파일
```

**작성 원칙:**
- 프로젝트 규칙·아키텍처처럼 **잘 안 변하는 내용은 여기 쓰지 말고 `CLAUDE.md` 에** 반영한다.
- 이 작업의 **목표·범위**는 `docs/specs/` 에 (있다면). 이 문서는 **"이번 세션 한정 상태"** 만 담는다.
- 사용자는 비개발자일 수 있다. 전문 용어를 쓸 때는 무엇을 뜻하는지 한 줄로 덧붙인다.
- 추측하지 말 것. 확인 안 한 내용은 "미확인"이라고 쓴다.

## 4. 접은 경로를 명세로 올린다 (빠뜨리면 반복 제안이 되살아난다)

방금 쓴 "고려했다가 안 한 것" 중 **이번 세션을 넘어 계속 유효한 항목**을 관련 명세
(`docs/specs/…md`)의 같은 이름 섹션에 옮겨 적고, 명세의 "변경 이력"에 한 줄 남긴다.

**왜 옮기는가:** 거절된 경로의 수명은 *세션*이 아니라 *작업 단위*다. 세션 문서에만 두면 세션과 함께
묻히고, `/devkit:resume` 은 최신 핸드오프 하나만 보므로 **세 세션 전에 거절한 제안이 다시 올라온다.**
반복 제안을 막으려고 만든 장치가 프로젝트가 커질수록 정반대로 작동하게 된다.

- 관련 명세가 없으면 이 단계는 건너뛴다. 다만 접은 항목이 여러 개면 `/devkit:spec` 을 제안한다.
- 항목이 이 작업을 넘어 프로젝트 전체에 계속 유효하면(아키텍처·데이터 배치 같은 것) 명세가 아니라
  `CLAUDE.md` 다. 이건 사용자에게 물어보고 옮긴다.
- 이번 세션 한정이거나 이미 뒤집힌 판단이면 옮기지 않는다.

## 5. 커밋 & 푸시

인계 문서만 담긴 별도 커밋으로 만든다(2단계에서 코드는 이미 커밋됐다).
명세를 고쳤으면 같은 커밋에 담는다 — 둘은 한 번의 정리 작업이다.

```
git add docs/handoffs/ docs/specs/
git commit -m "handoff: <설명>"
git push
```

**커밋된 인계 문서는 나중에 고치지 않는 것을 원칙으로 한다.** 내용이 달라졌으면 고치지 말고
새 인계 문서를 쓴다 — 과거 기록은 그 시점의 사실로 남겨두는 편이 읽는 사람에게 정확하다.
(다만 낡음 판정은 "최초 생성 커밋" 기준이라, 실수로 고쳐도 판정이 깨지지는 않는다.)

**원격이 있으면 푸시까지 반드시 끝낸다** — 푸시를 빠뜨리면 다른 기기에서 문서를 볼 수 없어
인계가 무의미해진다. 원격이 없거나 푸시가 실패하면 **원인과 함께 사용자에게 알린다**
(조용히 넘어가지 말 것).

## 6. 마무리 보고

- 저장된 파일 경로 (명세를 고쳤으면 그것도)
- 커밋 해시
- 푸시 성공 여부 (또는 왜 못 했는지)
- 한 줄 요약: 다음에 이어서 할 일

그리고 사용자에게 안내한다: **이제 `/clear` 로 컨텍스트를 비워도 안전하다.**
다음 세션에서는 `/devkit:resume` 을 치면 된다.
