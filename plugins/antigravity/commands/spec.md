사용자가 준 설명: $ARGUMENTS

이번 작업의 **의도**를 문서로 고정한다. 대화는 `/clear` 하면 사라지지만 이 파일은 남는다.
다른 기기에서, 몇 주 뒤에, 이 파일만 읽고도 **왜 이걸 하는지**가 이해되어야 한다.

## 0. 의도가 확정되지 않았으면 먼저 확정한다

목표·성공 기준이 아직 애매하면 `/devkit:clarify` 의 절차(조사 → 객관식 일괄 질문 → 되읽기)를
먼저 밟는다. **명세는 결정을 기록하는 문서지, 결정을 대신하는 문서가 아니다.**

## 1. 경로

`docs/specs/YYYY-MM-DD-NN-<슬러그>.md`

- 날짜는 시스템 날짜로 확인한다. 추측 금지.
- `NN` 은 그날의 순번(`01`, `02`, …). 두 자리 고정 — 파일명 정렬이 시간 순서와 일치해야 한다.
- 기존 파일을 덮어쓰지 않는다.
- `docs/specs/` 가 없으면 만든다.

## 2. 내용

```markdown
# <제목>

**날짜:** YYYY-MM-DD
**상태:** 진행 중 | 완료 | 보류 | 폐기

## 왜 하는가
지금 무엇이 불편하거나 부족한지. 이게 없으면 나중에 "이걸 왜 만들었지"가 된다.

## 목표
한 문단. 무엇이 가능해지는지.

## 성공 기준
무엇을 보고 "됐다"고 판단하는지. 확인 가능한 형태로.
- [ ] …

## 범위 밖
이번에 **안 할 것**. 이걸 적어두면 작업이 번지지 않는다.

## 제약
건드리면 안 되는 것, 반드시 지켜야 할 것. 있으면 **그 이유도** 적는다 —
이유 없는 제약은 나중에 누군가(사람이든 AI든) "개선"이라며 없앤다.

## 고려했다가 안 한 것
| 대안 | 왜 안 했나 |
검토 끝에 접은 경로. **이 섹션이 접은-경로의 정본(正本)이다.** `/devkit:resume` 은 최신 핸드오프
하나만 읽으므로, 여기 없는 거절 기록은 몇 세션 뒤 같은 제안으로 다시 올라온다. 작업이 진행되는
동안 `/devkit:handoff` 가 계속 여기에 항목을 추가한다 — 이 파일에서 유일하게 자라는 섹션이다.

## 열린 질문
아직 안 정한 것. 정해지면 이 파일을 고치지 말고 아래 "변경 이력"에 추가한다.

## 변경 이력
- YYYY-MM-DD: <무엇이 바뀌었나 / 왜>
```

## 3. 작성 원칙

- **잘 안 변하는 프로젝트 규칙·아키텍처는 여기 쓰지 말고 `CLAUDE.md` 에** 반영한다.
- **지금 이 순간의 진행 상태는 여기 쓰지 말고 `/devkit:handoff` 로** 남긴다.
- **`상태:` 를 정확히 유지한다.** `/devkit:resume` 은 관련 명세를 못 찾으면 `진행 중` 인 명세를
  전부 읽는다. 끝난 작업을 `완료`/`폐기`로 안 바꾸면 읽는 양이 계속 늘어난다.
- 이 파일은 **"왜 · 무엇을 · 어디까지"** 만 담는다. 셋의 역할 분리를 지킬 것:

  | 파일 | 담는 것 | 수명 |
  |---|---|---|
  | `CLAUDE.md` | 규칙, 아키텍처, 설계 근거 | 프로젝트 내내 |
  | `docs/specs/*.md` | 이 작업의 의도와 범위 | 작업 단위 |
  | `docs/handoffs/*.md` | 지금 어디까지 됐나 | 세션 단위 |

- 추측하지 말 것. 확인 안 한 내용은 "미확인"이라고 쓴다.

## 4. 커밋

git 리포지토리면 명세 파일만 담긴 별도 커밋으로 만든다.

```
git add docs/specs/
git commit -m "spec: <설명>"
```

리포가 아니면 커밋을 건너뛰고 **파일만 저장했다고 사용자에게 알린다**(조용히 넘어가지 말 것).

## 5. 보고

저장 경로, 커밋 여부, 그리고 **다음에 할 첫 번째 일** 한 줄.
