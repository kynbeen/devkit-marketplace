중단된 작업을 이어받는다. 사용자가 준 힌트: $ARGUMENTS

## 1. 최신 핸드오프에서 출발한다

`docs/handoffs/` 의 파일명은 `YYYY-MM-DD-NN-설명.md` 형식이라 **파일명 정렬 = 시간 순서**다.
따라서 최신 파일은 이름만 보고 찾는다 — git 조회가 필요 없다.

**기본값은 가장 최근 파일 하나다.** 핸드오프가 몇십 개로 늘어나도 평소 읽는 양은 1개다.

**단, 이건 출발점이지 상한선이 아니다.** 아래 중 하나라도 걸리면 **묻지 말고 더 읽는다**:

- 문서가 설명 없이 무언가를 가리킨다 (모르는 결정·용어·파일·"지난번에 정한 대로")
- 문서 내용이 실제 코드와 어긋난다
- "다음 단계"가 왜 그 순서인지 이해되지 않는다
- 사용자가 이번에 하려는 일이 이 핸드오프의 범위 밖이다

이때 볼 곳: 바로 앞 핸드오프 몇 개, `git log`/`git show`, 관련 `docs/specs/`, `CLAUDE.md`, `README`.
**막힌 채로 추측해서 진행하는 것보다 두세 개 더 읽는 편이 언제나 싸다.** 다만 무엇을 왜 더 읽었는지는
4단계 보고에 한 줄로 남긴다.

`docs/handoffs/` 가 없거나 비어 있으면: 그렇다고 알리고, 대신 `git log --oneline -10` 과
`CLAUDE.md`, `docs/specs/` 최신 항목을 훑어 현재 상태를 파악한 뒤 사용자에게 요약한다.

## 2. 낡음 판정 — 그 한 파일에 대해서만, 1회

PowerShell:
```powershell
$latest = Get-ChildItem docs/handoffs/*.md | Sort-Object Name | Select-Object -Last 1
$ref = git log --follow --diff-filter=A -1 --format=%h -- $latest.FullName
git log --oneline "$ref..HEAD"
```

bash:
```bash
LATEST=$(ls docs/handoffs/*-*.md | sort | tail -1)
REF=$(git log --follow --diff-filter=A -1 --format=%h -- "$LATEST")
git log --oneline $REF..HEAD
```

**결과가 비어 있으면** 문서가 최신이다. 그대로 이어받는다.

**커밋이 있으면** 그만큼 낡았다. 그 커밋들을 먼저 확인하고(`git show --stat`),
문서 내용 중 무엇이 더 이상 사실이 아닌지 **사용자에게 알린 뒤** 진행한다.

### 검사식을 이 형태로 쓰는 이유 — 세 가지 함정을 동시에 피한다

- *문서에 적힌 커밋 번호를 쓰면*: 문서는 커밋되기 **전에** 작성되므로 자기가 담길 번호를 적을 수
  없고, 핸드오프 커밋 자신이 항상 잡혀 매번 "낡음"으로 오판정된다. → 그래서 문서에 번호를 안 적는다.
- *`git log -1`(마지막 수정)을 쓰면*: 나중에 문서를 조금이라도 고치는 순간 기준점이 앞으로 끌려와
  그 사이의 **실제 작업이 통째로 숨겨진다**(더 위험한 방향의 오류). → 그래서 `--diff-filter=A`.
- *`--follow` 를 빼면*: 파일 이름을 바꾸는 순간 기준점이 리네임 커밋으로 밀린다. → 그래서 `--follow`.

이 조합이면 **과거 핸드오프를 수정하거나 이름을 바꿔도 판정이 깨지지 않는다.**

## 3. 배경 읽기 — 특히 이미 접은 경로

핸드오프의 "재개 시 읽어야 할 파일" 목록과 `CLAUDE.md`(아직 안 읽었으면)를 읽는다.

그리고 **명세를 반드시 읽는다.** 어느 것을 읽을지는 이 순서로 정한다:

1. 핸드오프 머리말의 **관련 명세** 가 가리키는 파일
2. 없으면 `docs/specs/` 에서 **`상태: 진행 중`** 인 것 전부 (보통 1~2개다)
3. 그것도 없으면 최신 명세 하나

명세에서 **"고려했다가 안 한 것"** 섹션은 빠짐없이 읽는다. **이미 접은 경로를 다시 제안하지 않기
위해서다** — 매 세션 같은 제안이 올라오는 것이 이 도구가 막으려는 가장 지치는 실패 모드다.

**핸드오프가 아니라 명세를 접은-경로의 근거로 삼는 이유:** 거절된 경로의 수명은 *세션*이 아니라
*작업 단위*다. 세션 문서에만 있으면 세션과 함께 묻히고, 세 세션 전에 거절한 제안이 다시 올라온다.
명세에 모아두면 핸드오프가 몇십 개로 늘어나도 **읽을 곳은 여전히 한 곳**이다.

접은 경로가 이 작업을 넘어 프로젝트 전체에 계속 유효한 성격이면(아키텍처·데이터 배치 같은 것)
`CLAUDE.md` 에 있어야 한다. 명세에서 그런 항목을 발견하면 사용자에게 옮기자고 제안한다.

## 4. 보고 후 착수

작업을 시작하기 전에 사용자에게 짧게 확인받는다:

```
이어받은 지점: <핸드오프 파일명>
현재 상태: <한 줄>
낡음: 없음 / 그 이후 커밋 N개 — <무엇이 달라졌는지>
다음 할 일: <핸드오프의 '다음 단계' 첫 항목>
```

사용자가 다른 걸 하려 할 수도 있으므로 **바로 코드를 고치지 말고 이 확인을 먼저 한다.**
