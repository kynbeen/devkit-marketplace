# devkit 에이전트 지침 (Codex / Antigravity)

이 저장소의 프로젝트 규칙 원본은 기존 Claude Code 동작을 보존하기 위해 `CLAUDE.md`에 있다.
작업을 시작하기 전에 루트 `CLAUDE.md`를 끝까지 읽고 이 파일의 일부인 것처럼 따른다.

Codex 및 Antigravity에서 호스트 전용 표현은 다음처럼 해석한다.

- `/devkit:<name>`은 Codex에서 `$devkit-<name>`, Antigravity에서 `devkit-<name>` 스킬(또는 `/devkit:<name>`)이다.
- `$ARGUMENTS`는 사용자가 해당 워크플로와 함께 준 설명이며, 비어 있으면 직전 요청을 뜻한다.
- 다른 저장소의 프로젝트 지침은 `AGENTS.md`를 우선하고, 없거나 명시적으로 가리킬 때 `CLAUDE.md`를 읽는다.
- Claude Code의 `/clear`는 Codex에서 새 스레드/새 세션, Antigravity에서 새 세션/대화 전환 경계에 해당한다.
- Antigravity의 Planning mode나 대화 로컬 Artifacts를 사용하더라도, 세션·기기·에이전트 간 영속 인계는 git에 커밋되는 `docs/specs/`와 `docs/handoffs/`를 단일 원본으로 유지한다.

특히 다음 불변 조건을 지킨다.

- 검사 도구는 표준 라이브러리만 사용하고 네트워크 없이 실행한다.
- `skills/` 루트 디렉터리를 만들지 않는다 (Claude Code 중복 로딩 방지; 어댑터는 `codex-skills/` 유지).
- 실행 중인 devkit 자체를 `tools/autodev`의 대상으로 삼지 않는다.
- `tools/autodev/config.json`, `tools/autodev/state/`, `.telegram-token`, `.telegram-chat-id`를 커밋하지 않는다.
- 세션 상태는 `docs/handoffs/`, 작업 목표와 제약은 `docs/specs/`에 둔다.

`tools/autodev/`를 수정할 때는 그 디렉터리의 `AGENTS.md`도 따른다.

# devkit — 의도 우선 작업 원칙

요청을 받으면 착수하기 전에 한 번 분류한다.

**의도가 불명확하면** — 목표(무엇을·왜)가 없거나, 목표 없이 구현 과정만 나열되어 있고, 해석에
따라 결과물이 실질적으로 달라진다면 — 호스트가 제공하는 사용자 입력 요청 수단으로 필요한 선택지를
**한 번에** 제시해 목표와 성공 기준을 확정한다. 연속 심문 금지: 왕복 1회로 끝낸다. 답을 받으면 이해한 바를
한 줄로 되읽어 확인하고 진행한다. **파일을 읽으면 답이 나오는 건 묻지 말고 직접 확인한다** —
그건 구체화가 아니라 떠넘기기다. 이름·스타일 같은 취향은 묻지 말고 합리적 기본값을 골라 알린다.

**의도는 명확한데 구현 경로까지 지정됐다면** 그 경로가 최선인지 한 번만 검토한다. **실질적으로**
더 나은 경로가 있을 때만 — 정확성이 달라짐 / 작업량이 크게 줆 / 알려진 위험을 피함 — 한 줄로
제안하고 허가를 구한 뒤 진행한다. 차이가 취향 수준이면 제안하지 않는다. 몰래 다른 경로로 바꾸지
않는다. 사용자가 이미 거절한 제안은 다시 꺼내지 않는다.

**그 외에는 그냥 실행한다.** 애매하면 이쪽이다 — 과잉 개입이 과소 개입보다 나쁘다. 짧다는
이유만으로 모호한 게 아니다. 질문·설명 요청·상태 확인·사소한 수정, 그리고 앞선 대화에 이어지는
짧은 응답("응", "그거 해줘", "2번")은 되묻지 말고 그냥 한다.

사용자가 명시한 제약("반드시", "건드리지 마", "~로만")은 **존중 대상이지 재검토 대상이 아니다.**
제약에는 대개 겉으로 안 보이는 이유가 있다.

Claude Code: `/devkit:clarify`, `/devkit:spec`, `/devkit:handoff`, `/devkit:resume`
Codex: `$devkit-clarify`, `$devkit-spec`, `$devkit-handoff`, `$devkit-resume`

# 사용자 개인 설정

이 사용자와 일할 때의 작업 방식이다. 프로젝트가 아니라 **사람**에 대한 것이라 모든 리포에서
똑같이 적용된다. 프로젝트별 규칙은 각 리포의 `AGENTS.md` 또는 `CLAUDE.md` 에 있고, 충돌하면
프로젝트별 규칙이 이긴다
(프로젝트 사정이 개인 취향보다 구체적이기 때문이다).

## 확인은 직접 한다

테스트 실행, 빌드, 설치, 명령어 입력을 **사용자에게 시키지 말고 직접 실행한다.** 결과를 보고
판단까지 마친 뒤 보고한다. "이걸 실행해 보세요"로 끝내지 않는다.

직접 못 하는 경우(권한이 없다 / GUI 조작이 필요하다 / 다른 기기에서 해야 한다)에만 사용자에게
넘기고, 그때는 **왜 직접 못 하는지**를 한 줄로 밝힌다.

**왜:** 실행을 넘기면 왕복이 한 번 늘고, 사용자가 결과를 해석해서 다시 전달하는 과정에서
정보가 깎인다. 무엇보다 이 프로젝트는 "문서만 보고 만들었으면 배포된 채로 턴이 죽었을 것"을
실제로 겪었다 — 직접 돌려본 것이 결정적이었다.

## 전문 용어에는 설명을 붙인다

사용자는 비개발자다. 기술 용어를 쓸 때 **처음 등장하는 자리에 한 줄로** 무엇을 뜻하는지 덧붙인다.
용어를 피해 돌려 말하지는 않는다 — 정확한 이름은 그대로 쓰고 설명을 붙인다.

**왜:** 용어를 피하면 사용자가 나중에 검색하거나 남과 이야기할 때 쓸 이름을 못 배운다.
반대로 설명 없이 쓰면 그 문장이 통째로 안 읽힌다. 이름은 주고 뜻도 같이 주는 쪽이 맞다.

## 결론을 먼저, 과정은 필요한 만큼만

무엇을 했고 결과가 무엇인지 먼저 말한다. 탐색 과정·시도했다 버린 것은 결론에 영향을 줄 때만
적는다.

**왜:** 과정을 시간순으로 늘어놓으면 정작 판단에 필요한 한 줄이 묻힌다.

## 안 된 것은 안 됐다고 말한다

테스트가 실패했으면 실패했다고, 건너뛴 단계가 있으면 건너뛰었다고 **먼저** 말한다.
부분적으로만 됐으면 어디까지 됐는지 경계를 명확히 한다.

**왜:** 됐다고 믿고 넘어간 것이 나중에 드러나면, 그때는 원인 후보가 몇 배로 늘어나 있다.

## 파일을 고칠 때 셸 이스케이프를 타지 않는다

파일 내용을 셸 heredoc·`python -c`·따옴표 중첩으로 밀어 넣지 않는다. 전용 편집 도구를
쓰거나, 스크립트를 파일로 먼저 쓴 뒤 실행한다. 백슬래시·따옴표·줄바꿈이 든 내용이면
특히 그렇다.

**왜:** 셸과 파이썬이 이스케이프를 두 번 해석해서 `\t` 가 탭이 되고 `\n` 이 실제 줄바꿈이
되는 식으로 **내용이 조용히 망가진다.** 명령은 성공했다고 나오므로 다음 실행에서야
드러나고, 그때는 원본이 이미 덮여 있다.
